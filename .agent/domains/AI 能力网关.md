# AI 能力网关

## summary

为多个宿主提供统一的 AI 能力层：配置、LLM 出口、MCP 工具、记忆与代理转发，宿主不重复实现。

## applies_when

- 项目 `type` 为 library 或 backend，且被两个以上宿主共用。
- 需要同时服务本地桌面进程与远端服务。

## core_concerns

1. **配置来源唯一**：`config.yaml` 是事实来源，env 只做覆盖；进程不依赖某个宿主注入才能启动。
2. **端口与生命周期可观测**：服务启动后写 `runtime/<service>.json`（port + pid），读取方校验 PID 存活。
3. **密钥不外泄**：上游密钥只从配置读取，不进入日志、错误响应或提交记录。
4. **协议转换正确**：Anthropic ↔ OpenAI 的端点、事件与 finish/stop 原因必须双向映射完整。
5. **记忆写入不破坏原文**：覆盖采用「新增成功后软标记旧条」，消费方跳过已作废条目。
6. **失败可判定**：依赖缺失、端口冲突、上游拒绝时给出明确错误码，不静默降级。
7. **安装链路可控**：重依赖放进 extras，轻量宿主不必安装向量库与 onnx。
8. **跨仓契约可验证**：导出 `contracts/*.json`，消费方读文件校验，不扫描源码。

## questions

- 配置改动由谁触发重载：宿主、文件监听，还是仅重启？
- 密钥归属：网关代持，还是透传客户端 key？两种模式如何切换？
- 记忆与向量库的 schema 归本仓还是宿主？
- 上游不可用时拒绝启动，还是以降级模式运行并标记？

## research

- MCP 规范的当前版本与鉴权方式。
- mem0 / fastembed / qdrant-client 在目标平台的 wheel 支持与体积。
- Qdrant local 模式的并发与锁行为。

## generates

- 配置加载与优先级实现
- 端口探测、进程守护、运行时状态文件
- LLM 客户端与代理转发层
- MCP 工具注册与参数 schema
- 契约导出文件

## verify

- `agent-gateway --check` 通过。
- 单测覆盖配置优先级、端口解析、协议转换、记忆写入语义。
- wheel 在干净 venv 安装后，prompts 与 ast-js 资源可读、入口可执行。

## pitfalls

- 只在宿主注入 env 时才正确工作，脱离宿主即失效。
- 端口每次重新探测导致漂移（服务自己占用端口后被跳过）。
- 日志或错误响应带上游请求体，泄露密钥与用户内容。
- 契约依赖同时扫描宿主源码，跨仓后静默失效。
