# 项目教训

## 格式

### <日期> <一句话标题>

- **场景**：发生了什么。
- **事实**：日志、测试或复现证据。
- **决策**：之后怎么做。
- **范围**：仅本项目 / 本技术栈 / 可能通用。
- **晋升**：未评估 / 已提议 / 已确认。

## 规则

- 只记录有证据的经验。
- 与已有条目重复时合并，不新增同义条目。
- 标记为“可能通用”的条目，需经用户确认才可写入种子库。

## 条目

### 2026-10-26 uvicorn 进程收到 SIGTERM 后不返回调用方

- **场景**：服务端把运行时状态文件的清理写在 `main()` 的 `try/finally`，退出后文件残留。
- **事实**：独立探针运行 `uvicorn.run(...)` 并在 finally 打印，SIGTERM 后探针从未打印；日志显示应用已优雅关闭。
- **决策**：生命周期清理放进 Starlette lifespan 的 shutdown 钩子；读取侧保留 PID 存活校验兜底。
- **范围**：可能通用（所有 uvicorn 常驻服务）。
- **晋升**：未评估。

### 2026-10-26 批量格式化会波及无关文件

- **场景**：给 `ruff format` 传入整个包目录，重排了 37 个未修改文件。
- **事实**：`git status` 出现大量与本任务无关的变更。
- **决策**：只格式化本次改动涉及的路径；批量格式化单独作为提交。
- **范围**：可能通用。
- **晋升**：未评估。

### 2026-10-30 检索工具“看起来相关”可能来自分数继承而非命中

- **场景**：`recall` 返回大量弱相关记忆，但结果里的路径/函数名足以让模型继续操作。
- **事实**：随机串 query 仍返回 0.554–0.564 的热层结果；episode 扩展把 sibling 分数写成 `seed*0.98`，实际相似度只用于排序；107 次历史 recall 中 19 次含 expanded，最多占 6/10。
- **决策**：相关性下限与扩展分数必须分别建模；扩展结果使用实际相似度并单独放入 `related`，不参与主结果排序。
- **范围**：可能通用（所有带 group expansion 的向量召回）。
- **晋升**：未评估。

### 2026-10-30 向量库分数是 numpy 标量，不能直接进 JSON

- **场景**：recall 改造部署后，冷层命中查询返回 `Object of type float32 is not JSON serializable`。
- **事实**：140 次批量调用中 27 次失败，全部来自冷层/扩展分数；`json.dumps` 不接受 `numpy.float32`。
- **决策**：Qdrant/mem0/余弦计算结果写入响应前统一 `float()`；回归测试断言返回类型是 Python `float`。
- **范围**：可能通用（所有 numpy 向量库输出）。
- **晋升**：未评估。

### 2026-10-30 检索噪声主要来自词法层的通用词命中

- **场景**：对 368 条历史 recall query 的 1496 条返回结果做相关性标注（口径：能否停止搜索）。
- **事实**：`lexical`（notes 关键词）层 742 条结果中只有 19 条相关（2.6%），236 条完全不相关（32%）；同批 `dense` 层相关率 27%。整体 precision@5 = 0.42、top1 相关率 39%、平均每条 query 只有 0.88 条相关结果。
- **决策**：notes 层的「覆盖率 ≥60%」不足以挡住通用词命中（中英 bigram 也会凑数），需要改为关键词共现或直接降权到不参与主结果。
- **范围**：可能通用（所有把关键词覆盖率当相关性判据的检索层）。
- **晋升**：未评估。

### 2026-10-30 标注可以交给子 Agent，但必须固定口径与输出结构

- **场景**：368 条 query × 5 条结果 = 1496 条判定，人工太慢。
- **事实**：拆成 8 个分片文件（每片 46 条 query，含 query、当时上下文 100 字、结果摘要 90 字），8 个子 Agent 并行，统一 prompt 给出三档定义与反例规则，各自写 JSON 到文件；合并后 368 键 / 1496 条判定全部长度校验通过，0 非法值。
- **决策**：自动标注可用于大批量评测；前提是口径写成可判定的规则（能否停止搜索 + 词面撞车反例），并让 Agent 写文件而不是在回复里贴 JSON。
- **范围**：可能通用。
- **晋升**：未评估。

### 2026-10-30 换模型后热层静默归零：混合分不能当余弦阈值

- **场景**：切到 jina-zh 并重建后，`recall` 的 `dense_hot` 恒为 0 条且 `error` 为 null，冷层与 notes 正常。
- **事实**：mem0 `search()` 的 `threshold` 作用于 `semantic_score`，但返回的 `score` 是 `(semantic + bm25) / max_possible` 的混合分。阈值过滤后只剩 1 条候选时 `max_possible` 仍为 2.0，0.7467 的余弦分被记成 0.3734；臂内二次用 `score < floor` 过滤，把唯一命中丢掉。同一查询在阈值 0.0 下混合分反而是 0.804（高于语义分 0.608），说明两者符号关系不稳定。另有两处叠加：`_build_recall_pipeline` 的 hot/cold 阈值取自常量而非 per-model 表；`delete_collection`+`create_collection` 后旧 mem0 实例在同一进程内检索失效，重启即恢复。
- **决策**：臂内一律读 `score_details.semantic_score`（`explain=True`）做过滤与排序；所有 floor 只从 `floors_for(tag)` 取；重建后必须重启服务再验证。
- **范围**：可能通用（任何在向量库混合检索之上再套余弦阈值的场景）。
- **晋升**：未评估。

### 2026-10-30 自采 gold 集不能用于跨模型对比

- **场景**：用历次 recall 结果标注出的 249 条 gold 评测换模型，jina 的 recall@5 只有 0.54，而 minilm 基线是 1.0，看起来新模型明显更差。
- **事实**：gold 的相关项本来就是从 minilm 自身结果里挑的，minilm 复现 1.0 是自证。抽查 3 条判为「缺失」的查询，jina 返回内容其实高度相关，只是 id 不在 gold 里。改为盲标（只给 query + 当时上下文 + top-5 摘要，不露模型与 gold）后，同 249 条查询：minilm precision@5 0.397 / top1 0.390 / 空返回 0%，jina 0.662 / 0.600 / 3.6%。
- **决策**：跨模型或跨管线比较必须重新盲标，或只用不依赖旧结果的绝对指标；gold 集只用于同系统回归。
- **范围**：可能通用（所有用自身输出构建评测集再比较改动的场景）。
- **晋升**：未评估。

### 2026-10-30 评测集停用：query 不等于用户意图

- **场景**：三轮盲标（严格阈值 / 放宽阈值 / 新口径提案）之后，用户判定「我的视角大部分查询与意图无关」，停止标注。
- **事实**：评测 query 由历史会话按关键词提取，与用户当时的真实意图不对应；同一串词在不同上下文里指的事可能完全不同。因此基于 query 判定的相关性，无论口径怎么切（是否把「给出正确符号名」计入相关），都只是测「和这串词的贴合度」。此前两轮 gold 还叠加了自采偏差（旧 gold 取自 minilm 自身结果）。
- **决策**：离线相关性评测停用，改为真实使用中的 case 驱动排查（用户贴出不满意的 query + 结果，用 `/api/retrieval/diagnose` 与 `/api/retrieval/stats` 定位单点）。仍可采信的只有不依赖意图的指标：不相关率（内容与 query 主题是否对得上）、空返回率、符号定位命中率。
- **范围**：可能通用（所有从历史日志提取 query 再做人工/模型标注的检索评测）。
- **晋升**：未评估。

### 2026-10-30 词法层应只做兜底，不与语义层抢位

- **场景**：notes（关键词覆盖率）命中会进入主结果，且分数 0.5-0.6 正好压在冷层下限 0.55 上。
- **事实**：976 条盲标判定里，notes 层不相关率 36.4%（242 条中 88 条），而 hot 1.5%、cold 8.2%。notes 虽只占结果 24.8%，却贡献了 72% 的不相关项。抽样 100 条验证：改成「语义层有命中时 notes 不进主结果」后，notes 占比 26.2% → 8.5%，空返回 12 条不变（语义层全空时 notes 仍兜底）。
- **决策**：`Pipeline(lexical_only_as_fallback=True)`，在 fusion 之后按层过滤；兜底命中仍走 `weak_match` 状态，不冒充语义命中。不要再靠调覆盖率阈值解决，那是把同一层内部的噪声挪来挪去。
- **范围**：可能通用（所有把词法/BM25 结果与向量结果混排、且分数区间重叠的检索层）。
- **晋升**：未评估。

### 2026-10-30 重排与查询纠正实测否决，别按方案直觉预留接口

- **场景**：检索层方案里写了 rerank 与 correct（CRAG）两个阶段，代码只留了协议和参数占位，长期没有实现。
- **事实**：实测两个都不成立。cross-encoder（`jinaai/jina-reranker-v2-base-multilingual`）常驻内存 +3402MB、20 条打分 417ms，且把不相关内容排到第一（embedding 排序本来是对的）；LLM 改写（mimo-v2.6-flash）对 4 条 no_match 查询救活 0 条，反把 2 条本来有结果的改坏，还有 2/10 输出成 markdown 段落无法使用，每次要 800 token。
- **决策**：协议与参数占位若长期没有实现，应删除而不是留着。占位会让后续判断误以为"能力已存在只是没启用"，也会让方案与代码长期对不齐。要做就一次做完并实测，否则不留。
- **范围**：可能通用（所有"先留接口以后接"的设计）。
- **晋升**：未评估。
